# i2 Analyze containerised solution - familiarisation brief

Author: Korin Taunton, Lead Architect
Source: i2 Ansible+CDK reference implementation (ansible-i2a 0.9) and i2 analyze-deployment-tooling (GitHub v3.3.0). This brief is the authoritative reference for building the Azure equivalent.

## What the two repos are

- ansible-i2a 0.9: i2's real deployment logic. Deploys i2 Analyze into an existing (brownfield) AWS VPC - Solr/ZooKeeper on dedicated EC2, PostgreSQL on RDS, Liberty on ECS Fargate. The logic lives in the Ansible collection `i2group.adt`. It consumes a pinned ADT tarball (analyze-deployment-tooling-3.2.2) and the i2 Analyze minimal toolkit.
- analyze-deployment-tooling (ADT, GitHub): a thin bootstrap. It pulls the client image `i2group/i2eng-analyze-containers-client:<version>` and runs the install scripts inside it. The Dockerfiles, `deploy`, `manage-environment`, `generateSolrSchemas.sh` and DB templates all live inside that client image, not in the git tree.

## Versions

- i2 Analyze 4.4.6.1, ADT 3.2.2 (the attached reference). Public ADT is v3.3.0 targeting i2 Analyze 4.4.7.
- Liberty base `i2group/i2eng-liberty:ubi-jdk17`; configured image tag `liberty_configured_redhat:base-demo-4.4.6.1`.
- Solr 9.9.0 (`i2eng-solr:9.9`), ZooKeeper 3.9.4 (`i2eng-zookeeper:3.9`), PostgreSQL 17 (`i2eng-postgres:17`). SQL Server shipped as `i2eng-sqlserver:2022-1` (not the deployed engine). Temurin JDK 17.0.18+8.
- Licence: EULA acceptance only, no key file. Liberty env `LICENSE=ACCEPT`; toolkit `LIC_AGREEMENT=ACCEPT`, `ACCEPT_EULA=Y`, `MSSQL_PID=Developer`.

## Deployment order (nothing to working i2)

Infra (CDK brownfield, two-pass): controller EC2 -> solr-zk (pass 1) -> RDS -> liberty-ecs (creates ECS task SG) -> read task SG -> solr-zk (pass 2, opens ZK 2281 + Solr 8983 to the task SG) -> generate inventory. Skipping pass 2 leaves Liberty unable to reach ZooKeeper.

App (Ansible): pull images + install (ADT + toolkit + shared config) -> pki -> stage toolkit to Solr -> solr_zk (ZK then Solr) -> postgres -> db_init (ISTORE) -> liberty_build (build+push configured image, generate DB scripts) -> solr_collections (generate schemas, upload configsets, create collections) -> liberty_ecs (register task def, run service) -> sanity_tests. Service order: ZooKeeper -> Solr -> PostgreSQL -> Liberty.

## Secrets and PKI (exact)

Backend: AWS Secrets Manager. Prefixes: passwords `i2a-bf`, PKI `i2a-bf/pki`.

Passwords (role provision_secrets, random 24-char if absent, never overwritten): db/postgres-password, db/dba-password, db/dbb-password, db/etl-password, db/i2etl-password, db/i2analyze-password (the Liberty app user), db/i2public-password, liberty/admin-password (adt-admin), solr-auth-password (used for BOTH Solr BasicAuth and ZK digest, user `solr`).

PKI (role pki): CA (cert+key). Leaf cert+key each for: postgres, solr, zookeeper, liberty, jwt (signing only), external_gateway_user (client mTLS to connectors). Conditional: rds-ca/cert when RDS.

Consumption: this reference injects secrets as ENV VARS via the ECS task `secrets:` block (SSL_PRIVATE_KEY, SSL_CERTIFICATE, SSL_CA_CERTIFICATE, JWT_PRIVATE_KEY/JWT_CERTIFICATE, DB_PASSWORD, ADT_ADMIN_PASSWORD, SOLR_HTTP_BASIC_AUTH_PASSWORD, ZOO_DIGEST_PASSWORD, plus outbound gateway certs). Solr/ZK write PKCS12 keystores to tmpfs. Postgres writes cert/key to /tmp then the image consumes them. The i2 container images also accept the *_FILE variants (file-based), which is the natural AKS mapping via CSI.

## Per-component contract

- Liberty (ECS): port 9443, context root `opal`, cpu 2048/mem 4096. Env: LICENSE=ACCEPT, DB_DIALECT=postgres, DB_SERVER, DB_PORT, DB_NAME=ISTORE, DB_USERNAME=i2analyze, DB_SSL_CONNECTION=true, ZK_HOST, ZOO_DIGEST_USERNAME=solr, SOLR_HTTP_BASIC_AUTH_USER=solr, SOLR_ZOO_SSL_CONNECTION=true, SERVER_SSL=true, GATEWAY_SSL_CONNECTION=true, LIBERTY_HADR_MODE=1, ADT_ADMIN_USERNAME=adt-admin. Secrets injected as above.
- Solr 9.9.0: port 8983 TLS, PKCS12 keystore/truststore on tmpfs, BasicAuth (security.json, user solr), ZK client over Netty TLS to :2281/is_cluster.
- ZooKeeper 3.9.4: secureClientPort 2281 (NettyServerCnxnFactory), quorum 2888, leader 3888, digest auth user solr, 4lw whitelist mntr,conf,ruok.
- Database: PostgreSQL 17 container `postgres-i2a`, 5432 (host 15432), SERVER_SSL=true, DB name ISTORE, volumes for data + /var/i2a-data.

## Config, schema, collections

- App config: i2 shared config `base-demo` (config_version 4) linked via `manage-environment -t link`. Baked into the Liberty image by `deploy -c base-demo -t package` (not mounted at runtime).
- IS schema (db_init): 8 steps via ephemeral postgres-client containers - create DB, roles, DBA login, pg_cron, grant, app users, static then dynamic scripts. SQL generated by `deploy -t generate-db-scripts`.
- Solr collections (solr_collections): schemas via `i2a_tools_redhat generateSolrSchemas.sh` (LIC_AGREEMENT=ACCEPT); 8 collections (main_index, match_index1, match_index2, highlight_index, chart_index, vq_index, recordshare_index, daod_index), numShards=4, replicationFactor=1.

## Image build

Configured Liberty built on-host by ADT `deploy -t package` from base `i2eng-liberty:ubi-jdk17` + the linked config, pushed to ECR. ADT itself runs inside `i2eng-analyze-containers-client:3.2.2`. Images pinned by name:tag, not digest.

## AWS to Azure mapping

CDK -> Bicep. ECS Fargate -> AKS (already built) or Container Apps. ECR -> ACR. Secrets Manager -> Key Vault. SSM Parameter Store -> App Configuration / KV. RDS PostgreSQL -> Azure Database for PostgreSQL Flexible Server (direct equivalent, matches i2's tested cloud DB) or Azure SQL MI (programme decision; SQL Server is a supported ADT engine but off i2's tested cloud path). ALB/NLB -> Application Gateway / internal Load Balancer + Entra. CloudMap/CloudWatch -> Azure Monitor / private DNS. S3 -> Blob Storage. EC2 Solr/ZK -> AKS StatefulSets. IAM -> managed identities / RBAC.

Portable (cloud-agnostic): the app config (base-demo, schema, security schema, fragments), the PKI design and secret contents, the ISTORE schema + db_init sequence, the 8 Solr collection defs, and the per-component container contract. Only the infra layer (CDK/ECS/ECR/SM/SSM/RDS/ALB/S3) is AWS-specific.

## Implications for the Azure build

1. The exact secret names/contents and PKI set are now known - generate them into Key Vault to match the ADT contract, no guessing.
2. Build the configured Liberty image by running `i2eng-analyze-containers-client:3.2.2` with our `base-demo` config (`deploy -t package`) via ACR Tasks or a k8s Job; push to ACR.
3. db_init and solr_collections run as k8s Jobs using the client/tools images, against the DB and SolrCloud.
4. Liberty/Solr/ZooKeeper on AKS; DB off containers (SQL MI decided; Postgres Flexible Server is the lower-risk match to i2's reference).
5. Secrets to pods as env (secretKeyRef) or files (CSI) - both accepted by the images.
